# WarpDrop protocol v2

One transfer protocol over any ordered, reliable transport that carries text and binary frames:
a WebRTC data channel (primary) or a WebSocket relay through the server (fallback).
Web and CLI implement the same spec; `fixtures/` holds the shared test data (regenerate with
`bun scripts/gen-fixtures.mjs` in `web/`).

## 1. Share code

`4821-amber-otter-kite-moth` = `<room_id>-<secret>`.

- `room_id`: 4 digits chosen by the server (6 when 4-digit picks keep colliding). Public.
- `secret`: 4 words from the EFF large wordlist (~52 bits), generated by the sender. Never sent to the server.
- Web link: `https://host/r/4821#amber-otter-kite-moth` (browsers never send the fragment).
- CLI accepts the code or the full link.

## 2. Signaling (WebSocket `/ws`, JSON text frames)

Every JSON frame, signaling or transfer, carries its type in `t`. The sender's peer id is always `"sender"`.

| Direction | Message |
|---|---|
| client → server | `create_room {v:2, client}` |
| server → sender | `room_created {room_id, token}` |
| sender → server | `resume_room {room_id, token}` → `room_resumed {room_id, peers:[peer_id]}`. After a drop the room lives 30 s, then receivers get `room_closed`. |
| sender → server | `close_room` (e.g. after 3 failed authentications) → everyone gets `room_closed` |
| receiver → server | `join_room {v:2, room_id, client}` |
| server → receiver | `joined {peer_id}` |
| server → sender | `peer_joined {peer_id, client}` |
| either → server | `signal {to, payload}`; server delivers `signal {from, payload}`. A receiver may only signal the sender: its `to` is ignored. |
| either → server | `relay_request {to}`; server sends `relay_ticket {peer_id, ticket}` to both |
| server → client | `peer_left {peer_id}`, `room_closed`, `error {code, message}` |

Nearby lobby messages are in section 7. Error codes: `not_found | room_full | rate_limited | bad_request | unsupported_version | relay_disabled`.
Limits: 1 sender, up to 10 receivers per room; one room per connection.

### Relay `/relay/<ticket>`

Server pairs the two sockets presenting the same single-use ticket (30 s expiry) and copies WebSocket
binary messages in both directions. Closed after 60 s idle. The server sees only ciphertext (section 4).

## 3. Handshake (first frames on any transport)

1. Both sides send `hello {t:"hello", v:2, client, device, pub}`; `pub` is an ephemeral X25519 public key (hex, 32 bytes).
2. Key derivation (all HKDF-SHA256):
   - `root = HKDF(ikm=utf8(secret), salt=utf8(room_id), info="warpdrop/2/root", 32)`
   - `keys = HKDF(ikm=ECDH(shared), salt=root, info="warpdrop/2", 64)`; `authKey = keys[0:32]`, `sessionKey = keys[32:64]`
3. `transcript = utf8("warpdrop/2") ‖ senderPub ‖ receiverPub ‖ senderDtlsFp ‖ receiverDtlsFp`
   where fingerprints are the raw 32-byte SHA-256 digests from the SDP `a=fingerprint` lines; on the relay they are omitted.
4. **Receiver sends `auth {t:"auth", mac}` first**, `mac = HMAC-SHA256(authKey, "recv" ‖ transcript)`.
   Sender verifies, then replies `auth {mac}` with `HMAC-SHA256(authKey, "send" ‖ transcript)` and sends `manifest`.
5. Handshake times out after 20 s. After 3 failed authentications the sender closes the room. A failure sends `cancel {reason:"auth_failed"}`.

`shortcut: HMAC-over-transcript with a 52-bit secret relies on the 20 s timeout and room close after 3 failures; upgrade to a PAKE (CPace) if codes get shorter.`

## 4. Relay framing

`hello` and `auth` frames are plaintext. Everything after is AES-256-GCM with `sessionKey`, sent as one WebSocket binary message per frame:

- plaintext = `kind(1) ‖ payload`, `kind` 0 = text (UTF-8 JSON), 1 = binary, 2 = keepalive (empty payload, sent every 20 s, dropped by the receiving transport so the server's 60 s idle limit cannot end a paused session)
- nonce (12 B) = `dir(4, big-endian) ‖ counter(8, big-endian)`; `dir` 1 = sender→receiver, 2 = receiver→sender; counter starts at 0 per direction and increments per encrypted frame (ordered transport, so the nonce is not sent)
- wire = `ciphertext ‖ 16-byte tag`

Before the cipher is enabled only text WebSocket messages (`hello`, `auth`) are valid; a binary message arriving early is ciphertext and is held until the cipher is ready. A decrypt failure or counter gap closes the connection.

## 5. Transfer

After the handshake, control messages are JSON text frames, chunk bytes are raw binary frames.

```
sender → manifest {files:[{id, name, size, type}]}        files keyed by id, never by name
receiver → request {id, offset}                           per file, in order
sender → file_start {id, offset}
sender → <binary chunks>                                  read from file.slice(offset).stream()
sender → file_end {id, hash}                              hash = xxhash64 (seed 0) of the whole file, 16 lowercase hex chars
receiver → file_done {id}                                 after bytes == size and hash matches
either → cancel {reason}                                  declined | user | auth_failed | hash_mismatch | protocol_error
receiver → ack {id, bytes}                                after every 4 MiB written to the sink
```

- Zero-byte file: `file_start` then `file_end`, no chunks.
- Flow control: sender keeps at most 32 MiB unacked and respects `bufferedAmount` high/low marks (16 MiB / 4 MiB).
  `ack` is sent after the sink accepted the bytes, so backpressure reaches from the receiver's disk to the sender's reader.
- Chunk size: `min(sctp.maxMessageSize, 256 KiB)` on WebRTC (64 KiB fallback), 256 KiB on the relay.
- Resume: after a transport drop the receiver sends `request {id, offset}` with the bytes it has; it keeps its hasher state.
  When `offset > 0` the sender re-hashes `[0, offset)` locally, then continues hashing as it sends.
- Optional `lane` field is reserved in `hello` capabilities and `file_start` for future parallel data channels (CLI↔CLI).

### Shutdown

The sender closes the transport right after it receives `file_done` for the last file. The receiver, after sending that final `file_done`, waits up to 2 s for the sender's close before closing itself. Without this the receiver's last frame can be lost when it hangs up straight away, and the sender never learns the transfer finished.

### Validation (receiver and sender, at the boundary)

- every control message matches its schema; unknown `t` is a protocol error
- `size` is a finite integer ≥ 0; at most 10 000 files; names ≤ 255 bytes
- the serialized `manifest` frame is at most 200 000 bytes and must fit the transport's max message size (it is one frame; both implementations advertise 256 KiB), so in practice about 2 300 files; senders refuse larger sets and ask the user to zip them
- `sanitizeName`: take the last path segment after `/` or `\`, strip control characters (including ANSI escapes) and `..`,
  replace characters illegal on Windows (`<>:"|?*`) with `_`, prefix `_` to Windows reserved names (`CON`, `NUL`, `COM1`…), never return an empty name
- a binary frame outside `file_start`/`file_end`, or bytes beyond `size`, is `protocol_error`
- receivers write to a temp name and finalise only after the hash matches; on failure the partial output is removed or the download aborted

## 7. Nearby (same network, no share code)

A second way to meet. The transfer protocol (sections 3-5) is unchanged; only discovery, the room's admission rule and the handshake's authentication differ. Share codes still work exactly as before.

### Lobby

A client opens `/ws?lobby=1` (same path, so proxies need no change; counted in a separate per-IP connection pool) and sends `nearby_join {v:2, device, client, hidden?}`. A lobby socket may send only `nearby_*` messages and every other socket none of them.

The server groups clients by network: the same public IPv4, the same IPv6 /64, or any private/loopback/link-local address.

| Direction | Message |
|---|---|
| client → server | `nearby_join {v, device, client, hidden}` → `nearby_joined {peer_id, devices:[{peer_id, device, client}]}`. `hidden` clients see the list and can send, but are not listed and cannot be invited |
| server → client | `nearby_peer {peer}`, `nearby_peer_left {peer_id}` |
| client → server | `nearby_leave` |
| sender → server | `nearby_invite {to, room_id, token}`; `token` proves the sender created the room |
| server → target | `nearby_invite {peer, room_id, ticket}` |
| target → server | `nearby_decline {room_id, ticket, reason}`; `reason` is `declined` or `busy`; spends the ticket |
| server → sender (room socket) | `invite_declined {peer_id, device, reason}`; `peer_id` is the `to` it invited |

Limits: 50 devices per network. A client in the lobby cannot also be in a room on that connection.

### Gated rooms

The sender creates its room on a normal `/ws` socket with `create_room {nearby:true}`. Such a room admits a receiver only with `join_room {ticket}`: single-use tickets issued by `nearby_invite`. An unknown or spent ticket gets `not_found`, the same answer as a missing room. `joined` carries a fresh `ticket` so the receiver can rejoin after its signaling socket drops. Senders give up on an invite nobody answers after 60 s.

### Handshake without secret words

The secret is the empty string, so `root = HKDF(ikm="", salt=room_id, ...)` and the MACs only prove both sides derived the same keys. What stops a man-in-the-middle is a 6-digit code both users compare:

1. Sender: `hello {pub:"", commit}`, `commit = hex(SHA-256(senderPub))`. The receiver sends nothing yet.
2. Receiver, having seen the commitment: `hello {pub}`.
3. Sender: `reveal {pub}`. Receiver checks `SHA-256(pub) == commit`, otherwise `protocol_error`.
4. `auth` frames as in section 3.
5. `sas = uint32_be(HMAC-SHA256(authKey, "sas" ‖ transcript)[0:4]) mod 10^6`, zero-padded to 6 digits. Both sides display it before the receiver accepts.

The order matters: the sender fixes its key before it sees the receiver's, and the receiver fixes its key before the sender reveals, so an attacker cannot choose keys that make the two sides' codes match. Each side's code is then effectively a 1-in-10^6 guess.

`shortcut: the code authenticates the session only if the users actually compare it, and it does not stop someone on the network from asking to send. Receivers must accept each transfer. Upgrade path: remembered devices with long-term identity keys.`

Test vectors: `fixtures/crypto-vectors.json` key `nearby`.

### Direct connection on the local network (native clients only)

Browsers cannot do mDNS or open sockets, so this exists only between CLI, Android and desktop apps. It needs no server, so it works offline. Web clients are reached through the lobby as above.

**Discovery**: DNS-SD service `_warpdrop._tcp` on `local.`. Instance name = a random per-process id. TXT: `v=2`, `id=<same id>`, `name=<device label>`, `client=<cli|mobile|...>`. SRV/A/AAAA give the TCP port and addresses (link-local IPv6 is skipped: it cannot be dialed without a zone). A device is also in the lobby list under the same `device` label; clients merge the two lists by that name and prefer the direct route, falling back to an invite when the dial fails.

**Roles**: the dialer is the sender, the listener is the receiver. `room_id` is the constant `"lan"`, the secret is empty, so the handshake is exactly section 7's code-less one and both users compare the 6-digit code.

**Framing**: the relay's (section 4), with the WebSocket message replaced by `type(1) ‖ len(4, big-endian) ‖ data`: `type` 1 = text, 2 = binary; `len` at most 1 MiB. Anything else closes the connection. Text only before the cipher is enabled; after, every frame is sealed and keepalives run as on the relay. Writes block on the socket, which is the backpressure.

**Receiver rules** (anyone on the network can connect): one connection is handled at a time and others are closed at once; handshakes time out after 20 s; an address whose offer was declined or cancelled is ignored for 30 s; the user is asked for every transfer. There is no resume: a dropped connection fails the transfer and the sender starts again.
